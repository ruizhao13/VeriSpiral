# 第一轮问题验证：最短路径与可检查证书

这是一轮已执行的公开开发试验，检验如何把问题表现转成协议改进。
输入为本仓库专门构造的数学问题，不含真实研究资料；结果范围仅限下列图与代码。

运行 `make path-trial`。原始契约在[试验计划](../examples/path/experiment_plan.json)，
第一轮观察后形成的修复在[补证书计划](../examples/path/witness_repair_plan.json)。
可核查[完整报告](../examples/expected/path-trial/path_trial_report.json)、
[主实现](../src/verispiral/path_workflow.py)、
[分别编写的穷举参考与路径评分](../src/verispiral/path_reference.py)，以及
[证书与修复测试](../tests/test_path_workflow.py)。这些链接是本文数值和软件行为的证据。

## 问题形式化与可验证性

本次问题段落：给定小型有向无环图，边带整数权重（可以为负），从节点 0 到最后
一个节点返回总权重最小的路径。结果必须在原图上有效，且不能被另一条路径改进。

| Problem Charter 项目 | 分类与本次处理 |
| --- | --- |
| 最小化路径总权重、源点与终点、允许负权 | 上述公开输入明确规定 |
| 编号按拓扑顺序、没有重边、最多 12 个节点 | 为小型精确试验增加的显式范围假设 |
| 本轮生成的图从源点可到达所有节点 | 便于构造有限整数势函数；不能代表一般图 |
| 路网拥堵、风险、环境变化 | 未纳入这个数学问题，不能声称解决真实路线规划 |
| 检查锚点 | 无剪枝枚举全部路径，并从原始边权独立评分候选 |

这是 exact-certifiable 类型。Goal 是原图最优性，Setup 是公开小图；候选方法为
逐步选最便宜出边的 greedy 与按拓扑顺序求解的 exact。两者都实际执行，返回路径与
势函数提案。参考实现不复用候选求解器或证书检查代码，但也是同一模型体系分别编写，
因此属于实现交叉核查，不能声称完全独立的科学验证。

## 第一轮：加强验证器会解决什么

在同一问题和候选上依次比较三个预先写好的开发版本：仅检查路径可行性、
只检查路径边的证书、检查全部边的证书。前两个被明确保留为有缺陷的对照，
不注册为可信门禁，也不代表已获得用户接受的科研规格。

最小反例有四条边：`0→1:1`、`1→3:9`、`0→2:2`、`2→3:1`。
greedy 返回成本为 10 的路径；另一条路径成本为 3。
仅查可行性会接受前者，沿自身路径构造的势函数也能骗过“只查路径边”的版本。
检查遗漏边后就无法认证它。这同时提供了算法非最优和弱验证器误接受两项证据，
不能强行归入一个单故障标签。

两张开发图加 24 张公式生成的公开回归图，各运行两个候选，共 52 次候选评价：

| 检查方式 | 被当作最优而接受 | 其中实际非最优 | 实际最优但未验证 | 接受集合的最大成本后悔 |
| --- | ---: | ---: | ---: | ---: |
| 仅查可行性 | 52 | 8 | 0 | 8 |
| 仅查路径边证书 | 52 | 8 | 0 | 8 |
| 全边证书 | 30 | 0 | 14 | 0 |

后悔是候选成本减去该图穷举最优成本；每项均由独立路径评分计算，不信任被审计
验证器报告的成本。这个表是同一候选池的检查对照，不是等总预算的工作流效果评价。
52 项来自 26 张图，不能当作 52 个独立科研任务；图也不是随机抽样的真实问题。

## 完整证书为什么成立

候选提交一条路径和每个节点的整数势 `p[v]`。检查源点 `p[0]=0`，原图中每条边
`p[v] <= p[u] + w(u,v)`，并要求提交路径的重算成本 `C = p[t]`。
任意源到终点路径上的不等式相加，得到其成本至少为 `p[t]-p[0]=p[t]`。
提交路径恰好达到这个下界，因此在本次原图目标下最优。

这段直接推导依赖完整查边、有效路径和精确算术。代码拒绝布尔值、浮点数、NaN、
重边、错误端点和不完整势函数。它不证明原图包含所有现实机制，也不证明无路可达。
[测试](../tests/test_path_workflow.py)包括漏查边、源点未锚定、伪造成本等攻击，
并在 27 张三节点图上枚举 6,534 个路径/势函数组合交叉核查认证结果。

## 第二轮：修复证书，不改变候选路径

第一轮的 14 项未验证最优结果说明：完整检查不会自动提供完整证书。
因此补证书计划绑定了第一轮汇总哈希，保持图、目标、greedy 返回路径和检查规则
不变，只用已有 exact 方法生成完整势函数。其计算作为证书建造成本收费。

重跑全部 26 条 greedy 路径：26 条都保持不变，18 条实际最优路径全部得到认证，
8 条非最优路径仍未认证；误接受为 0，实际最优但未验证从 14 降为 0。
另对已公开的 27 张三节点图及负权反例检查修复后的候选。
这些是追加回归覆盖，不能称作新发现的隐藏测试或泛化评价。

`unverified` 只表示证书不能支持最优性，不等于“路径非最优”。只有与原图穷举结果
比较后，报告才标记算法非最优。修复的是证书可用性，不是这 26 条路径的质量。

## 成本结果没有支持加速主张

证书构造和完整检查都需要处理全部边；直接 exact 方法本来就会计算所需势函数。
补证书方案重新执行这个方法，并额外保留 greedy 计算与检查，因此没有取得相对
直接求解的计算优势。这个负结果必须保留，不能只与昂贵穷举比较后宣称加速。

例如报告中的 `complete-8-7` 有 28 条边：穷举遍历 127 次边，直接 exact 松弛 28 次。
补证书的 greedy 使用 7 次出边检查与 29 次证书相关边操作，此外还有两次图校验与
两次邻接索引扫描，各 56 个边条目；随后检查器另做原图校验与证书检查。
这些是不同组件的操作计数，不是运行时间；列表、整数位长与人工设计成本未测量，
没有从未测量项推导总成本优势。参考评分也单列为评价开销。

## 根据表现改了哪些协议

| 观察 | 项目改进 | 后续检查 |
| --- | --- | --- |
| 坏算法同时骗过弱检查器 | 诊断允许同时记录算法与验证器问题 | 保留两个有缺陷版本及原反例 |
| 好结果可能附带坏证书 | 分开记录候选质量与证书有效性，允许单独补证书 | 路径不变、最优结果恢复认证、非最优仍不认证 |
| 补证书包含完整求解 | 强制计入证书生产成本，加入有竞争力的直接方法对照 | 不宣称本轮产生加速 |
| 重测会暴露测试信息 | 每轮保留观察、修复计划与回归边界 | 不把开发反馈改称最终测试 |
